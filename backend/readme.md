# Backend: Умный кредитный кабинет

FastAPI-сервис кредитного конвейера для малого и микробизнеса. Принимает заявку клиента, проводит её через проверки, обогащение данными (БКИ, ЕГРЮЛ, ФНС), скоринг и кредитное решение, ведёт журнал всех переходов статуса и даёт сотруднику банка очередь заявок и ручное решение.

Общая архитектура и запуск всего проекта: [корневой README](../README.md). Здесь описан только backend.

## Как это работает

```
клиент: создать заявку (DRAFT) → отправить (submit)
                                     │
                        конвейер (синхронно, один запрос)
                                     ▼
   SUBMITTED → VALIDATION → ENRICHMENT → SCORING → решение
                   │             │                    │
          INFO_REQUESTED     UNDERWRITING     APPROVED / COUNTER_OFFER /
        (данные неверны)  (источник недоступен)  REJECTED / UNDERWRITING
```

1. **Валидация.** Сумма и срок проверяются по лимитам продукта, цель должна быть указана. Ошибки приводят к статусу `INFO_REQUESTED`: клиент исправляет заявку и отправляет её снова.
2. **Обогащение.** Запросы к БКИ, ЕГРЮЛ и ФНС (в демо это сервис `mocks`). Результат сохраняется в заявке. Если источник недоступен, заявка уходит на ручной разбор, а не получает отказ: сбой на стороне банка не должен становиться отказом клиенту.
3. **Скоринг.** Прозрачная балльная модель (базовый балл 500, факторы дают плюс или минус). Каждый сработавший фактор сохраняется в заявке, поэтому оценку можно объяснить.
4. **Кредитное решение.** Отдельный слой поверх скоринга. Учитывает стоп-правила, крупные суммы, флаги ручного разбора, пороги скора и лимиты продукта. Исход не бинарный: одобрение, отказ, другие условия или ручной разбор.
5. **Ручной разбор.** Сотрудник банка видит заявку в очереди и принимает решение с обязательным комментарием.
6. **Журнал.** Каждый переход статуса пишется в `application_events` (из статуса, в статус, кто, комментарий, время).

Подробно: [`docs/scoring.md`](../docs/scoring.md) (веса, пороги, правила), [`docs/state-diagram.md`](../docs/state-diagram.md) (диаграмма состояний), [`docs/test-scenarios.md`](../docs/test-scenarios.md) (сценарии проверки).

**Конвейер синхронный.** Ответ на `POST /applications/{id}/submit` уже содержит итоговый статус (`APPROVED`, `REJECTED` и т. д.), поэтому опрашивать статус после отправки не нужно. Промежуточные этапы (`VALIDATION → ENRICHMENT → SCORING`) видны в массиве `events`.

## Структура кода

```
app/
├── main.py                  # приложение FastAPI, CORS, создание таблиц и seed при старте
├── api/
│   ├── __init__.py          # api_router с префиксом /api/v1
│   └── routes/
│       ├── catalog.py       # продукты и компании
│       ├── applications.py  # клиентские действия и решение андеррайтера
│       └── bank.py          # очередь заявок для сотрудника банка
├── core/                    # config.py (настройки), db.py (сессия SQLAlchemy)
├── integrations/external.py # клиенты БКИ / ЕГРЮЛ / ФНС (httpx → mocks)
├── models/                  # entities.py (таблицы), status.py (статусы)
├── schemas/__init__.py      # pydantic-схемы запросов и ответов
├── services/
│   ├── pipeline.py          # конвейер: валидация → обогащение → скоринг → решение
│   ├── scoring.py           # балльная модель
│   ├── decision.py          # кредитное решение, стоп-правила, флаги, ставка
│   └── state_machine.py     # таблица разрешённых переходов статусов
├── seed.py + seed_data/     # синтетические продукты и компании
tests/                       # pytest
```

## Запуск

Переменные окружения (см. также корневой README):

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./local.db` | строка подключения SQLAlchemy |
| `MOCKS_BASE_URL` | `http://localhost:8081` | адрес сервиса моков БКИ/ЕГРЮЛ/ФНС |
| `CORS_ORIGINS` | `http://localhost:3000` | разрешённые origin через запятую |
| `LOG_LEVEL` | `INFO` | уровень логирования |
| `APP_ENV` | `local` | имя окружения |
| `JWT_SECRET` | `change-me` | зарезервировано под авторизацию |

Целиком через Docker (из корня репозитория):

```bash
docker compose up --build
```

Локально, с `uv`:

```bash
cd backend
uv run uvicorn app.main:app --port 8000 --reload
```

Локально, без `uv`:

```bash
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1          # Windows PowerShell; на Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --port 8000 --reload
```

Для полного сценария нужны запущенные моки (порт 8081). Если моки недоступны, заявки не падают с ошибкой, а уходят на ручной разбор с причиной «Не получены данные: ...».

При первом старте таблицы создаются автоматически и загружаются тестовые данные. Чтобы начать с чистой базы локально, удалите `local.db`.

После запуска: Swagger `http://localhost:8000/docs`, проверка живости `GET /health`.

## Для фронтенда: API

Все эндпоинты имеют префикс **`/api/v1`**. Исключение: `GET /health`. Формат: JSON, UTF-8. Идентификаторы заявок и компаний это UUID-строки.

### Каталог

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/products` | кредитные продукты: код, название, лимиты суммы и срока, базовая ставка, цели |
| GET | `/companies` | тестовые клиенты (вместо авторизации выбор в шапке) |
| GET | `/companies/{id}` | один клиент |

### Клиентский путь

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/applications?company_id=&status=` | список заявок, новые сверху |
| POST | `/applications` | создать черновик. Тело: `company_id`, `product_code`, `amount`, `term_months`, `purpose`. Ответ 201 |
| GET | `/applications/{id}` | карточка: данные, `score`, `decision`, `enrichment`, `events` |
| PATCH | `/applications/{id}` | изменить `amount`, `term_months`, `purpose`. Только в `DRAFT` и `INFO_REQUESTED`, иначе 409 |
| POST | `/applications/{id}/submit` | отправить в банк (из `DRAFT`) или повторно после уточнений (из `INFO_REQUESTED`). Запускает конвейер, ответ содержит итоговый статус |
| POST | `/applications/{id}/accept` | принять предложение (`APPROVED` или `COUNTER_OFFER` → `SIGNING`) |
| POST | `/applications/{id}/sign` | подписать документы (`SIGNING` → `ISSUED`, симуляция) |
| POST | `/applications/{id}/cancel` | отозвать заявку |

### Банк

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/bank/queue` | очередь заявок для сотрудника (без черновиков) |
| POST | `/applications/{id}/underwriter-decision` | решение сотрудника по заявке в статусе `UNDERWRITING` |
| GET | `/applications/{id}` | карточка заявки: тот же эндпоинт, что у клиента |

**`GET /bank/queue`** принимает параметры (все необязательные):

| Параметр | Значения |
|---|---|
| `status` | любой статус, например `UNDERWRITING` |
| `min_score`, `max_score` | границы скора |
| `sort` | `created_desc` (по умолчанию), `created_asc`, `score_desc`, `score_asc`, `amount_desc` |
| `limit` | 1–500, по умолчанию 100 |

Элемент очереди: `id`, `company_id`, `company_name`, `inn`, `product_code`, `amount`, `term_months`, `score`, `status`, `reason`, `created_at`, `updated_at`. В `reason` лежит причина решения или ручного разбора, её удобно показывать прямо в таблице.

**`POST /applications/{id}/underwriter-decision`**

```json
{
  "status": "APPROVED",
  "comment": "Финансы подтверждены",
  "amount": 1000000,
  "term_months": 12,
  "rate": 16.5
}
```

- `status`: только `APPROVED`, `COUNTER_OFFER`, `REJECTED`, `INFO_REQUESTED`. Другие значения дают 422.
- `comment`: обязателен, минимум 3 символа.
- `amount`, `term_months`, `rate`: необязательны, для `APPROVED` и `COUNTER_OFFER`. Если не заданы, берутся из заявки и продукта. Для `COUNTER_OFFER` нужно указать хотя бы одно условие.
- Заголовок **`X-Actor`**: имя сотрудника, попадает в журнал событий и в `decision.decided_by`. HTTP-заголовки передают только ASCII, поэтому имя нужно кодировать: `encodeURIComponent("Иванова А.")`. Сервер декодирует сам. Если заголовка нет, актором будет `underwriter`.

### Коды ошибок

| Код | Когда |
|---|---|
| 404 | заявка, компания или продукт не найдены |
| 409 | действие недопустимо в текущем статусе (например, подписать отклонённую заявку), либо заявка не на ручном разборе |
| 422 | неверное тело запроса (нет комментария, запрещённый статус, отрицательная сумма), сумма или срок вне лимитов продукта в решении сотрудника |

Тело ошибки: `{"detail": "..."}` для 404 и 409, для 422 список ошибок валидации.

## Статусы заявки и доступные действия

Какие кнопки показывать на каждом статусе:

| Статус | Что видит клиент | Действия клиента | Действия банка |
|---|---|---|---|
| `DRAFT` | черновик | редактировать, отправить, отозвать | нет |
| `SUBMITTED`, `VALIDATION`, `ENRICHMENT`, `SCORING` | промежуточные: в обычном сценарии клиент их не видит, конвейер проходит за один запрос | нет | нет |
| `INFO_REQUESTED` | нужно исправить данные, причина в последнем событии | редактировать, отправить повторно, отозвать | нет |
| `UNDERWRITING` | «Заявка на рассмотрении у специалиста» | отозвать | одобрить, другие условия, отказать, запросить данные |
| `APPROVED` | предложение: сумма, срок, ставка | принять, отозвать | нет |
| `COUNTER_OFFER` | предложение на других условиях | принять, отозвать | нет |
| `SIGNING` | подписание документов | подписать, отозвать | нет |
| `ISSUED` | средства выданы (конечный) | нет | нет |
| `REJECTED` | отказ, причина в `decision.reason` (конечный) | нет | нет |
| `CANCELLED` | отозвана (конечный) | нет | нет |

Конкретная причина `INFO_REQUESTED` в поле `comment` последнего события из `events`.

## Форматы данных

**Заявка** (`GET /applications/{id}`):

```json
{
  "id": "…", "company_id": "…", "product_code": "EXPRESS",
  "status": "APPROVED",
  "amount": "2000000.00", "term_months": 24, "purpose": "Оборотные средства",
  "score": 710,
  "decision": {
    "amount": 2000000.0, "term_months": 24, "rate": 16.0,
    "reason": "Скор 710 ≥ 600",
    "factors": [
      {"name": "Положительная кредитная история", "delta": 80},
      {"name": "Бизнес старше 2 лет", "delta": 60},
      {"name": "Низкая долговая нагрузка", "delta": 70}
    ]
  },
  "enrichment": {
    "bki": {…}, "egrul": {…}, "fns": {…},
    "failed_sources": []
  },
  "events": [
    {"id": 1, "from_status": "SUBMITTED", "to_status": "VALIDATION",
     "actor": "system", "comment": null, "created_at": "2026-10-24T12:00:00Z"}
  ],
  "created_at": "…", "updated_at": "…"
}
```

Важные детали:

- **Числа типа Decimal** (`amount`, `base_rate`, лимиты продукта) приходят строкой. Приводите к числу через `Number(...)`. Числа внутри `decision` (`amount`, `rate`) приходят обычными числами.
- **`decision`** заполняется после конвейера и может быть `null` у черновика. Поля `amount`, `term_months`, `rate` равны `null` при отказе и на ручном разборе. `decided_by` появляется после решения сотрудника.
- **`decision.factors`** это разбивка скора: список объектов `{name, delta}`. Её удобно рисовать как список плюсов и минусов. Если источник был недоступен, список пуст.
- **`enrichment.failed_sources`** содержит названия недоступных источников (`bki`, `egrul`, `fns`). Непустой список означает, что заявка ушла на ручной разбор из-за сбоя, а не из-за свойств клиента.
- **`events`** отсортированы по времени создания. Подходят для таймлайна. `actor`: `client`, `system` или имя сотрудника.
- Даты в ISO 8601, UTC.

**Продукт** (`GET /products`): `code`, `name`, `description`, `min_amount`, `max_amount`, `min_term_months`, `max_term_months`, `base_rate`, `purposes`. Лимиты используйте для валидации формы на клиенте: сервер всё равно проверит их и вернёт `INFO_REQUESTED`.

## Тестовые клиенты

Вместо авторизации выбирается клиент. Данные в моках синтетические. Рекомендуемые суммы для демо подобраны так, чтобы получить описанный исход (продукт `EXPRESS`, лимиты 100 000 – 5 000 000 ₽, срок 3–36 мес.):

| Клиент | ИНН | Сумма | Результат |
|---|---|---|---|
| ООО «Ромашка» | 7701000001 | 2 000 000 ₽, 24 мес. | `APPROVED`, скор 710, ставка 16 % |
| ООО «Василёк» | 7701000002 | 2 000 000 ₽ | `REJECTED`, скор 190 |
| ИП Петров П. П. | 770100000003 | **300 000 ₽**, 12 мес. | `UNDERWRITING`, скор 470, «Бизнес младше 12 месяцев» |
| ООО «Лютик» | 7701000004 | любая | `REJECTED`, «Компания не действует по данным ЕГРЮЛ» |

Петров на 2 000 000 ₽ получит отказ (нагрузка 0,8 при выручке 2,5 млн ₽): это ожидаемое поведение, а не ошибка.

## Известные ограничения

- **Авторизации нет.** Клиент выбирается из списка, сотрудник банка определяется заголовком `X-Actor` без проверки. `JWT_SECRET` зарезервирован под будущую авторизацию.
- **Конвейер синхронный.** Подходит для демо. Для нагрузки этапы стоит вынести в очередь задач с воркерами; тогда клиент будет опрашивать статус.
- **Таблицы создаются через `create_all`**, а не миграциями. Для продакшена нужен Alembic.
- **Скоринг упрощён**: прозрачная балльная модель вместо статистической. Допущения и пороги описаны в [`docs/scoring.md`](../docs/scoring.md).
- **Подписание документов и выдача средств** смоделированы без реальных операций.
